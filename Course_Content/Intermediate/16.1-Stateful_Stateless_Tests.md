# Stateless vs Stateful Unit Testing

When writing unit tests, one of the most important concepts is understanding whether your tests depend on shared state.

A well-designed unit test suite should generally be **stateless**.

## What is State?

State is simply data that exists at a point in time.

In our Contact List application, examples of state include:
```java
List<Contact> contacts
```

or
```java
Contact contact =
    service.findById(1L);
```

The information currently stored in memory represents the application's state.

Example:
```text
Current State

Contact #1
Contact #2
Contact #3
```

If we delete a contact:
```text
New State

Contact #1
Contact #3
```

The state has changed.

## Stateless Testing

A stateless test does not depend on another test running first.

Each test creates its own setup data and can run independently.

### Example
```java
@Test
void shouldAddContactSuccessfully() {

    Contact contact = new Contact(
        1L,
        "John",
        "Smith",
        "john@email.com",
        "5551234");

    service.addContact(contact);

    assertEquals(
        1,
        service.getAllContacts().size()
    );
}
```

This test:

1. Creates its own contact
2. Adds the contact
3. Verifies the result

It does not care about:

* Previous tests
* Future tests
* Test execution order

This is a stateless test.

## Why Stateless Tests Are Preferred

Imagine these tests:
```java
@Test
void testA() {
    service.addContact(contact);
}

@Test
void testB() {
    assertEquals(1,
        service.getAllContacts().size());
}
```

If:
```text
testA runs first
```

then:
```text
testB passes
```

But if:
```text
testB runs first
```

then:
```text
testB fails
```

The tests are now dependent on execution order.

This is a major problem.

## Characteristics of Stateless Tests

A stateless test:

✅ Creates its own data

✅ Sets up its own environment

✅ Can run alone

✅ Can run in any order

✅ Produces the same result every time

## How @BeforeEach Helps

Recall our setup method:
```java
@BeforeEach
void setup() {

    repository = new ContactRepository();

    service = new ContactService(repository);
}
```

Before every test:

1. Create Repository
2. Create Service
3. Run Test


Then for the next test:

1. Create NEW Repository
2. Create NEW Service
3. Run Test


Every test gets a clean environment.

This is one reason why our ContactService tests are stateless.

## Stateful Testing

A stateful test depends on state created somewhere else.

Example:
```java
@Test
void shouldCreateContact() {

    service.addContact(
        new Contact(
            1L,
            "John",
            "Smith",
            "john@email.com",
            "5551234"
        )
    );
}

@Test
void shouldContainOneContact() {

    assertEquals(
        1,
        service.getAllContacts().size()
    );
}
```

The second test assumes:

A contact already exists

But where did it come from?

From another test.

This creates a dependency.

The tests are now stateful.

## Why Stateful Tests Are Dangerous

Suppose your test suite contains:
```text
Test A
Test B
Test C
```

Stateful tests often assume:
```text
A runs first
B runs second
C runs third
```

However, modern testing tools may execute tests:
```text
C
A
B
```

or even
```text
B
C
A
```

The result:
```text
Random failures
```

These are often called:

    Flaky Tests

Flaky tests pass sometimes and fail sometimes.

Developers quickly lose trust in them.

## Example Using Our Update Contact Test

Consider our working test:
```java
@Test
void shouldUpdateContactSuccessfully() {

    Contact contact = new Contact(
            1L,
            "John",
            "Smith",
            "john@email.com",
            "5551234");

    service.addContact(contact);

    service.updateContact(
            1L,
            "new@email.com",
            "9999999");

    Contact updated =
            service.findById(1L);

    assertEquals(
            "new@email.com",
            updated.getEmail());
}
```

Why is this stateless?

Because the test:
```java
Creates Contact
Updates Contact
Verifies Contact
```

Everything needed exists inside the test itself.

No dependencies exist.

## A Stateful Version of the Same Test
```java
@Test
void shouldUpdateContactSuccessfully() {

    service.updateContact(
        1L,
        "new@email.com",
        "9999999");

    Contact updated =
        service.findById(1L);

    assertEquals(
        "new@email.com",
        updated.getEmail());
}
```

Question:

Where did Contact #1 come from?

Answer:
```text
Unknown
```

The test now assumes a contact already exists.

This hidden dependency makes the test fragile.

## State Leakage

State leakage occurs when one test leaves behind data that affects another test.

Example:
```java
@Test
void shouldAddOneContact() {

    service.addContact(contact);

    assertEquals(
        1,
        service.countContacts());
}
```

Later:
```java
@Test
void shouldAddSecondContact() {

    service.addContact(contact2);

    assertEquals(
        1,
        service.countContacts());
}
```

If the repository isn't reset between tests:
```text
First Test = 1 contact

Second Test = 2 contacts
```

Unexpected failure.

The state leaked from one test to another.

## Testing State Changes

Although unit tests should be stateless, we frequently test that the application's state changes correctly.

For example:
```java
@Test
void shouldDeleteContactSuccessfully() {

    Contact contact = new Contact(
            1L,
            "John",
            "Smith",
            "john@email.com",
            "5551234");

    service.addContact(contact);

    assertEquals(
            1,
            service.countContacts());

    service.deleteContact(1L);

    assertEquals(
            0,
            service.countContacts());
}
```

Notice:
```text
Initial State = 1 Contact
Final State = 0 Contacts
```

We are testing state transitions, but the test itself remains stateless because it creates its own data.

This distinction is important.

## Stateful Systems vs Stateless Tests

Students often confuse these concepts.

A system may be stateful:
```text
Shopping Cart
Bank Account
Contact List
Inventory System
```

Yet the unit tests should still be stateless.

Example:
```text
Application = Stateful

Tests = Stateless
```

This is the ideal design.

## Real Interview Question
**Question**

Why should unit tests be independent?

Strong Answer
```text
Unit tests should be independent so they can run in any order and always produce the same result. Independent tests are more reliable, easier to maintain, and less likely to fail because of hidden dependencies or shared state.
```

## Best Practices
**Always Use @BeforeEach**
```java
@BeforeEach
void setup() {
    repository = new ContactRepository();
    service = new ContactService(repository);
}
```

Creates a fresh test environment.

**Build Test Data Inside the Test**

Good:
```java
Contact contact =
    new Contact(...);
```

Avoid:
```text
Assume contact already exists
```

**One Test, One Behavior**

Good:
```java
shouldRejectInvalidPhone()

shouldUpdateContact()

shouldDeleteContact()
```

Avoid giant tests that perform multiple unrelated actions.

**Never Depend on Execution Order**

Bad assumption:
```text
Test A runs first
```

Good assumption:
```text
Every test stands alone
```

# Key Takeaway

The easiest way for students to remember the difference is:

**Stateless Test**

>Everything needed for the test is created inside the test (or setup method).
```Text
Create Data
Execute Code
Verify Result
```
**Stateful Test**

>The test depends on data or actions from somewhere else.
```text
Assume Data Exists
Execute Code
Hope Previous Test Ran
```
**Golden Rule**

>Applications are often stateful, but unit tests should be stateless.

This principle leads to faster, more reliable, and more maintainable test suites and is considered a hallmark of professional Java development.
